1. Executive summary

Cloud Workspace is a team collaboration app: group chat, video meetings, ephemeral calls, file storage, tasks, and workspaces with admin controls. A college developer built it in four intense days — August 15 to 18, 2026 — using OpenCode AI agents for nearly all implementation. The app went from an empty Next.js scaffold to a deployed product on a free-tier cloud stack within roughly 96 hours.

This report consolidates that entire process. I read the full OpenCode session database for the project (74 sessions, 4,783 messages), both git repositories (61 commits), the generated migration chain, and the current source tree. Each phase below names the sessions and commits that produced it, so every claim traces back to evidence.

The shape of the project is unusual and worth stating plainly. Day 1 built the whole product surface — UI shell, chat with a Socket.IO server, tasks, meetings, uploads, auth, workspaces — in about twelve hours. Day 2 moved the infrastructure to a deployable free-tier stack: Turso, UploadThing, and a new Cloudflare Worker repo. Day 3 matured realtime video and added calls, PostHog, and OAuth. Day 4 was supposed to be routine hardening. Instead it exposed the deepest defect in the project: the chat feature had shipped a realtime transport that could never work in production, hidden behind a REST polling fallback. The day ended with that defect root-caused, fixed in both repositories, verified against the live site with an instrumented browser, and written up — followed by a second, subtler production bug (meetings invisible across devices) found and fixed the same evening.

Three numbers frame the story. About 9.1 million input tokens and 1.6 million output tokens of model activity produced 22,949 lines of tracked TypeScript and CSS. Recorded model cost totaled roughly ten dollars, because most sessions ran cheap flash-tier models. And the distance between "the build passes" and "the product works" — the gap this project kept falling into — closed only when verification moved from curl probes to a real browser driving the real deployment.

4. Phase 1 — Stack foundation

Sessions: ses_ffbb808a · Commit: 2c239d8 "first commit"

The project started at 12:47 on August 15 with one instruction: set up Drizzle with SQLite, Better Auth with OAuth, Docker Compose, and shadcn. The session hit three version quirks immediately and documented them for every future agent:

  • Better Auth's CLI schema generation failed under Bun (its better-sqlite3 dependency), so it ran under plain Node. Generated output goes to db/schema.ts, which must never be hand-edited because regeneration overwrites it.
  • drizzle-kit 0.31 removed the driver config key; adding it fails validation.
  • Better Auth 1.6 rejects a body on sign-out; navigation happens client-side after authClient.signOut().

The foundation landed in five minutes of session time: libsql client in db/index.ts, four auth tables migrated, shadcn initialized on the Radix + Nova preset, a Docker Compose stub, and a demo page proving OAuth round-trips. Verification was already strict: typecheck, Biome lint, and a production build before declaring done.

The tooling decisions made here never changed: Bun as the only package manager, Biome instead of ESLint, tsc --noEmit as the gate before any build, and the React Compiler enabled, which bans manual memoization across the whole codebase.

5. Phase 2 — Product UI and design language

Sessions: ses_ffbac1a0 (UI build), ses_ffb9c958 (UX rewrite) · Commit: a7765a9 "new stuff"

The user's brief was specific: a cloud workspace in the style of Notion and Linear, light theme only. They pasted Linear's actual computed CSS as reference. The session translated the token system rather than copying desktop-only rules — cool neutral surfaces, compact borders, indigo interaction color, and Inter typography — and kept the app scrollable and selectable where Linear is not.

The first build produced the whole workspace chrome in one client component: sidebar, header, search dialog, create menu, profile menu, and views for home, inbox, messages, files, calls, and people, with local interaction state standing in for a backend. A follow-up UX session then found the honest defects in its own output: Inbox and People were unreachable, ⌘K was advertised but not wired, dialogs ignored Escape, buttons fired dead toasts, and roughly 200 lines of legacy view code lingered. The rewrite unified navigation, cleared unread dots on visit, and verified every flow in a live browser through Next's MCP endpoint plus agent-browser — an early appearance of the browser-first verification habit that became decisive on day 4.

6. Phase 3 — Chat, built by parallel agents

Sessions: orchestrator ses_ffb9ba50 → fork ses_ffb916ef; subagents ses_ffb87c03 (routing), ses_ffb87c02 (DB), ses_ffb81d92 (REST), ses_ffb81d91 (WebSocket server), ses_ffb7d1df (UI) · Commit: folded into a7765a9

Chat was the first feature to get the full engineering treatment, and the session shows the project's characteristic method at its best. The orchestrator planned six phases, wrote the shared type contract itself, snapshot the existing UI for later comparison, and spawned phases in parallel with hard boundaries: the DB agent could not touch components/; the API agent could not touch db/; nobody ran a dev server.

6.1 The routing refactor

Phase 0 split the by-now 1,962-line components/workspace-shell.tsx into the route group that still defines the repo: app/(workspace)/ pages per feature, shell chrome in components/shell/, view bodies in components/views/. The constraint was byte-identical rendering — same classes, same DOM order, same behaviors — with navigation switched from local state to next/link and usePathname(). Compliance was checked mechanically: a diff script compared every className token in the new files against the pre-refactor snapshot and reported zero real losses.

6.2 Data, API, transport, UI

  • DB (ses_ffb87c02): four tables in a new db/chat.ts (conversation, conversation_member, message, message_reaction), deliberately separate from the Better Auth-generated schema. Migration 0001_naive_dark_beast.sql. An idempotent seed script creates five demo users, three channels, four DMs, 32 staggered messages, reactions, and engineered unread counts (Samarth gets exactly three unread in # product).
  • REST (ses_ffb81d92): six routes under app/api/chat/ covering conversations, paginated messages, send, DM creation, read markers, and reaction toggles, with signed-out users getting a read-only preview of seeded data. Dynamic params typed as Promises per the Next 16 docs.
  • Transport (ses_ffb81d91): a standalone Socket.IO server, ws/server.ts, validating Better Auth session cookies at handshake, joining conv:<id> and user:<id> rooms, persisting messages, and emitting the event vocabulary that still exists today: message:new, message:sent, message:failed, conversations:changed, reaction:update, typing. This is the artifact that, unknown at the time, defined a protocol no production host would ever speak.
  • UI (ses_ffb7d1df): conversation list with unread badges, thread with date separators and load-older, optimistic composer with rollback, eight-emoji reaction popover, typing indicator, new-message dialog, mobile list↔thread swap. Two correctness catches stand out: the server echoes message:new to the sender, so a pending-send map swaps the optimistic message instead of duplicating it; and a race where a socket event landing during initial fetch would be overwritten — fixed by merging rather than replacing.

The orchestrator's own review pass then found and fixed two cross-client sync gaps before calling the feature done. Total elapsed time from plan to verified: about 55 minutes of wall-clock time, with five agents working concurrently.

7. Phase 4 — Feature sweep

Sessions: tasks ses_ffaf9745, meetings ses_ffaf74af, uploads ses_ffaf29b3, auth ses_ffae8cc5, workspaces ses_ffae7762, landing ses_ffa9db3c, home ses_ff9c386b, meetings admin ses_ff9b1899, docker ses_ffa9b450 · Commits: mostly inside a7765a9; e15e286, 9066982, 9fcffac, d343a0a, 3b509cb, 7fce290, 66031a5

With chat proven, the afternoon replicated the pattern across every remaining surface — usually several features in flight at once.

7.1 Tasks

A task manager with list, calendar, todo, and timeline views, then drag-and-drop between them, file attachments from the uploads area, user mentions, and reminders that materialize as inbox notifications when their time passes. This session also produced the first data-layer incident: a stale Drizzle snapshot referenced a deleted migration file, db:migrate silently half-applied changes, and the recovery rebuilt the local database from scratch — acceptable because all data was seed data, and the journal-vs-reality mismatch was documented.

7.2 Meetings and video

Meeting tables and API joined the stack, and ws/server.ts grew WebRTC signaling: presence, offer/answer/ICE relay. The room UI is a full-screen mesh call — local preview, remote tiles with mic/cam/share states, mute, screen share, invite links, host end-for-all. The session caught a genuine distributed-systems bug in review: glare, where both peers create peer connections and send offers simultaneously, deadlocking negotiation. Fix: only the newcomer initiates.

7.3 Files and uploads

Uploads to local disk under public/uploads/ with folders, list/grid views, sorting, renaming, and drag-and-drop. Bugs found by use: dragging a grid photo re-uploaded it as a file (fixed by checking dataTransfer.types for "Files"), and clicking images opened new tabs until a lightbox with keyboard navigation replaced them. File-type icons were later redrawn as hand-built multi-tone SVG glyphs in components/files/file-glyphs.tsx after the user asked for macOS-style detail.

7.4 Auth and multi-tenancy

A sign-in/sign-up page arrived with seeded demo accounts and a shared demo password — convenient, and, as the day-2 security audit later flagged, a critical exposure if ever left in a public deployment. Workspace isolation landed the same day: workspace and workspace_member tables with admin/member roles, Samarth as admin, workspace scoping added to every read and write including the WebSocket server, a settings page with invite/role/remove flows guarded by a last-admin check, and live verification that member Maya gets 403s and that a fresh signup sees zero Cedar data.

7.5 Product polish

Landing page for signed-out visitors, a real logged-in home page (the user asked the agent to interview them about what belongs there), collapsible sidebar with live-meeting indicator, avatar and logo uploads with client-side compression, mobile responsiveness passes, and Docker Compose wiring the dev server and the Socket.IO process.

8. Phase 5 — First debugging stories

Sessions: ses_ffa94984 ("bun run ws not working"), ses_ffb02d21 (layout fixes)

On the first evening the user reported that messages would not send in some chats, and that some chats showed every message as sent by "Jordan Lee." The investigation is worth retelling because it previewed the project's failure modes in miniature.

Database timestamps showed test messages alternating between u-samarth and u-jordan — the user had been playing both sides of a conversation in two windows. A ghost session made it worse: a user row deleted by a reseed left its session row behind, so one window held credentials for a person who no longer existed and silently received the read-only preview. Meanwhile the running Socket.IO process kept a stale file handle on a replaced sqlite.db and acknowledged writes into the void. Code was never broken; identity and process state were. Remediation deleted the polluted test conversation, cleared chat data at the user's request, reseeded, and wrote the lessons down — including "restart bun run ws after any reseed," which later entered AGENTS.md.

9. Phase 6 — The $0 deployment plan and audits

Sessions: strategy Q&A ses_ffa9aa89, orchestrator ses_ff95b1a1 (+ forks ses_ff8a1c8c, ses_ff8a16c2), audits ses_ff95915a×2, integration check ses_ff95662a, research ses_ff8a3774/ses_ff8a3775/+2, plan ses_ff89fd7b

Late on day 1 the user asked how to deploy for free. The answer defined the rest of the project. The app's needs mapped onto four services: Turso for the database (libsql-compatible, same client), UploadThing for file blobs (serverless hosts have ephemeral disks), Vercel for the Next.js app, and Cloudflare Workers with Durable Objects for realtime. The reasoning was candid about trade-offs: Socket.IO cannot survive on Vercel; chat could ship degraded on REST polling, but calls would be dead without a socket; Workers' Hibernation API makes idle connections nearly free; and WebRTC media is peer-to-peer anyway, so the Worker only relays the handshake.

The research subagents gathered version facts that steered concrete choices: uploadthing 7.7.4, @libsql/client/web 0.17.4, wrangler 4.x (Node-only install), DO Hibernation GA with up to 32,768 sockets per object, and a warning that turned prophetic — every code deploy restarts Durable Objects and drops open connections.

Two audits then inventoried production risks. The findings that mattered most:

  • The signed-out "preview" mode fell back to the first workspace in the database on every read path — a data leak waiting for a second tenant.
  • Meeting rooms accepted unauthenticated joins and relayed WebRTC signals to anyone with a meeting ID; guests could flip scheduled meetings to live.
  • The Socket.IO server reflected any Origin with credentials enabled.
  • Demo credentials were hardcoded in the sign-in UI; open signup had no rate limiting or email verification.
  • Uploads trusted client-declared MIME types and served user content from public/ — a stored-XSS pattern.
  • SQLite foreign keys were declared but never enforced per connection; cascades did not cascade.

The orchestrator session converted all of it into a phased plan — Turso, UploadThing, Worker with token auth and origin allowlists, security headers, error boundaries, health checks — and the user approved the four-service architecture in ses_ff95b1a1 with the words that set day 2's agenda. Notably, this 301-message session died mid-pass and survives as a fork; the framework restarted the work without a checkpoint. That interruption pattern recurs.

10. Phase 7 — Infra migrations

Sessions: UploadThing ses_ff69ea22, Turso ses_ff688ae9, worker dev-vars ses_ff656f7a; icons ses_ff69ac7d, favicon ses_ff68c3c2, fonts ses_ff6510dc, rebrand ses_ff64e6d5 · Commits: e25c925, bc1e37f, f426ebb, 36b108e, 3699dd7, ee14313, 876425e, fd3f7fb, cabc92f; worker 5ee6df0, d119a92, b1c5ab2

10.1 UploadThing

Filesystem writes gave way to UploadThing v7 route handlers with session-aware middleware, utapi.deleteFiles on deletes, and URL helpers that always produce utfs.io links. The user asked for a hard cap, and got a three-layer one: middleware rejects the request before bytes transfer when a workspace exceeds 100 MB, the insert path re-checks inside a transaction (two concurrent uploads cannot both slip through; the blocked upload's remote file is deleted), and a shared helper computes usage from live rows including legacy ones. A storage pill on the files page turns amber at 80% and rose at 100%. A backfill script migrated nine legacy files plus the workspace logo, reusing already-uploaded keys after its first run crashed post-upload pre-database-update — the kind of partial-state bug the retry logic now guards against.

10.2 Turso

The web libsql client replaced the file client for production, health checks arrived, and db/index.ts learned to fail fast: production without TURSO_DATABASE_URL throws at startup, verified by a clean-environment test. Migrations moved into the deploy itself — db:deploy runs before next build on Vercel, so a failed migration fails the deployment, which the plan explicitly wanted. Workspace deletion now purges remote UploadThing objects.

Two follow-up incidents taught the env-precedence lesson early. With both DATABASE_URL and TURSO_DATABASE_URL present, the client preferred Turso unconditionally and the developer's local login broke against an unseeded cloud database — fixed in ee14313 so development reads SQLite and production reads Turso. Then the user asked for data parity; a filtered INSERT-only dump (117 statements) brought all twelve tables to identical row counts, demo passwords included.

10.3 The realtime worker repo

The user asked whether the Worker should live in its own repository; the answer was yes, and cloud-workspace-realtime was born: wrangler config, a RealtimeRoom Durable Object, origin allowlist, loopback allowances for local dev, upgrade-header preservation through the DO, meeting signaling, and later a call:hangup broadcast and round-trip tests. Authentication moved from cookies to short-lived JWTs minted by /api/realtime/token, because the Better Auth cookie lives on the Vercel domain, not the Workers domain. The shared WS_AUTH_SECRET mismatch (31-char vs 64-hex) was caught before it could bite.

10.4 Identity

The visual identity settled in the same window: PixelArticons replaced lucide, Schibsted Grotesk took headings and Hanken Grotesk body text, a favicon went through six iterations to a rounded white app-grid tile, and "Cedar & Co." became Cloud Workspace everywhere.

11. Phase 8 — Realtime matures

Sessions: video fixes ses_ff648429, calls ses_ff63f124, explore ses_ff63ee98, mobile login ses_ff63aa98, landing nav ses_fef66932, PostHog ses_fef47bb6, OAuth ses_fef279de · Commits: 501f6cf, a61ebf5, e277f6c, 2e2a1bc, 7c7f760, cf762bc, d504530, ac1343a, 1c3db79, 8fdf08f; worker 949191a, 4fda148, 5548bae, 50b5f99

After the WS migration, video calling broke — the first direct consequence of moving transports. Fixes rolled in over a day: connecting the meeting room to the worker's protocol (501f6cf), allowing LAN origins in dev so a phone could hydrate (a61ebf5), and the subtlest one, a camera that stayed dark because getUserMedia resolved before the video tile mounted — the stream existed but was never attached, fixed by reattaching on mount and on device toggles (cf762bc). When a black frame persisted, frame-level browser checks proved the track live and identified the controlled browser's synthetic camera as the culprit, not the code.

Calls arrived as a deliberate contrast to meetings: short-lived one-on-one or group rooms that die when ended, versus persistent meeting rooms. Lifecycle: created ringing, first non-host join flips live, host ends or a heartbeat sweep auto-ends anything silent past 90 seconds. Entry points cover the calls page, a new-call dialog, and a call panel embedded in chat headers. Its launch 500'd instructively — migration 0009 had been applied to Turso while dev read sqlite.db, so no such table: call — resolved by applying migrations to the file the app actually reads, plus a shell-quoting lesson about empty-string environment overrides.

Analytics and identity closed the day: PostHog with provider, masking, user identification, logout reset, and browser-verified ingestion; OAuth credentials wired for GitHub and Google with the practical guidance that GitHub allows one callback URL while Google allows many. Chat gained message grouping by sender/time. Landing nav became a floating pill with scroll-spy after a visible fight with backdrop whitespace.

12. Phase 9 — Production finale, part one

Sessions: secrets scan ses_fec5f2b0, audits ses_fec4eaa0/ses_fec4eaa1, workers deploy ses_fec4d642, DO explainer ses_fec4d506, dead code ses_fec31789 + ses_fec3158d, env triage ses_fec0bd8b, invalid origin ses_fec04814 · Commits: 10f7d64, ed05abb, a80478b, 0331dc5, 23f0532, 5862564, e5b34de

Morning of August 18 opened confidently: the Vercel project had zero environment variables at 12:18, the worker deployed cleanly, and the audit checklist was in hand. Then the failures started, each one teaching something.

12.1 Dead code and the build that broke twice

A knip-driven sweep removed 312 lines across 18 files — dead exports, unused types, an orphaned component — and the session honestly logged collateral damage: the edit tool mangled three unrelated files mid-sweep, all restored byte-identical from HEAD before committing (23f0532). The user's alarmed "what did you do to the git history" was answered with evidence: linear history, clean tree, nothing lost.

The first Vercel build failure was pure process: lib/recents-data.ts existed locally but was never committed, so the cloud clone couldn't resolve it. Commit 0331dc5 captured the pending recents/analytics work. Lesson: local builds prove nothing about what Vercel clones.

12.2 The guard and the localhost leak

The second failure came from the HTTPS guard added in 10f7d64: local builds saw VERCEL=1 because vercel link had left an OIDC token in .env.local, and .env still said BETTER_AUTH_URL=http://localhost:3000. Commit 5862564 relaxed the guard with a localhost regex — and the transcript preserves the assistant talking itself out of it minutes later: "you're right to push back — that's a band-aid, and it weakens a guard you intentionally added." The proper fix (scope the guard to VERCEL_ENV production/preview) landed shortly after among the env-validation changes that rode along with e5b34de, and stands today.

12.3 Invalid origin

Production login then failed with Better Auth's "Invalid origin." The chain, untangled in ses_fec04814: the freshly mass-added Vercel variables lacked BETTER_AUTH_TRUSTED_ORIGINS (added), the CSP blocked PostHog's scripts (e5b34de allowed the host), and — found by probing the worker — its deployed ALLOWED_ORIGINS secret was http://localhost:3000 only, rejecting the production origin outright. Fixed and verified with a signed token over HTTP/1.1, after discovering that HTTP/2 silently strips the Upgrade header and turns every probe into a lie. One more trap surfaced when the user asked why /messages 500'd: the Vercel value for NEXT_PUBLIC_WS_URL was literally ws://localhost:3001, copied upward from an old env file, and lib/client-config.ts correctly threw at module evaluation. The codebase contained no localhost; the configuration did. The session declared victory on a curl returning {"ok":true} — the last time that standard would pass.

13. Phase 10 — Root cause diagnosis

Sessions: ses_febf8a7d (+ fork ses_feaac294)

Frustrated, the user asked the direct question: why can't the AI finalize this project — why does localhost keep coming back? The answer, produced by reading the project's own session history, is the intellectual core of this report and worth quoting:

"The AI treats your local dev environment as the production source of truth, and when prod breaks it patches the code to tolerate localhost instead of reconfiguring the deployed env."

The supporting evidence, each item traceable to a named session or commit:

  1. Flash-tier models did the production work. Every deploy-focused session ran deepseek-v4-flash variants — tuned for fast iteration, inclined to treat a passing build as done, and prone to verifying with curl rather than the product.
  2. The guard-relaxation commit. 5862564 widened a production check so the wrong configuration passed, instead of fixing the configuration.
  3. Environment sprawl. .env.prod held a placeholder domain and an empty URL that would crash the client config; .env.vercel held literal [SENSITIVE] strings saved from a masked pull. Every "sync the env" action copied from the local file upward, propagating localhost.
  4. The repository re-taught localhost every session. AGENTS.md — injected into every agent's instructions — described Socket.IO on ws://localhost:3001 as the realtime design, because that was what the code did. The docs were a faithful carrier of a broken architecture.
  5. Interruptions counted as completions. Steps ended with "finish": "error", "Step interrupted"; whole readiness passes survived only as forks, redone from scratch without checkpoints.

The user proposed the remedy in the same session: scour code and env, fix once, deploy, then verify with browser control and the Vercel CLI — frugally, on the free tier. That plan became the next phase, and it worked.

14. Phase 11 — The real fix: chat realtime on the worker

Sessions: ses_febf8a7d/ses_feaac294 (continued) · Commits: worker da0806f; app 534aecc, 8448d78, cf152ac

The scour found the blocking defect within minutes: the browser spoke Socket.IO; the deployed worker spoke native WebSocket JSON frames; its chat handler was a stub that broadcast literal pings. Production chat had never had realtime. The REST-plus-polling fallback had absorbed the failure so completely that four days of demos looked healthy.

14.1 What changed

  • Worker (da0806f): new src/chat.ts mirrors the app's chat data layer as plain SQL over the same Turso database — membership and existence checks, message inserts, conversation and read-marker updates, reaction aggregation, avatar presentation. src/realtime.ts grew real handlers: Connection holds a set of rooms instead of one; joins validate membership and workspace; sends persist then fan out message:new, ack the sender with message:sent, and notify lists via conversations:changed; reactions toggle in Turso and broadcast aggregates; typing excludes the sender. Turso bindings entered wrangler.toml and secrets.
  • Client (8448d78): components/chat/chat-socket.ts rewritten around native WebSocket while preserving its entire public API, so no UI call site changed. Token fetched per connection, exponential backoff, and — fixing a latent Socket.IO-era gap — automatic chat:join replay for every known conversation on reconnect. The Socket.IO server, dependencies, npm script, and compose service were deleted. Documentation was corrected at the source: AGENTS.md stopped teaching the localhost architecture.
  • Env hygiene: .env.prod and .env.vercel deleted; BETTER_AUTH_TRUSTED_ORIGINS restored for local login; Vercel dashboard declared the single source of production truth.

14.2 Ship sequence and the stale instance

Order mattered: worker first, app second, one CLI production deploy per batch. The first browser test then produced the day's finest debugging moment — the socket connected, frames went out, nothing came back, nothing persisted. A probe against a never-used room name answered instantly with new-code behavior; the old chat room stayed silent even for the stub's echo. Conclusion: Cloudflare keeps a Durable Object instance on the code that created it, for up to thirty days. A migration to destroy instances proved forbidden in a single step, so the surgical fix won: bump the room name. cf152ac moved clients to ?room=chat2, the redeploy landed, and the same test passed end-to-end.

14.3 Proof, not claims

An init script wrapped window.WebSocket before app bundles ran and logged every frame. Against the live site it captured the full loop: chat:join out, typing out, message:send out; message:new, message:sent, conversations:changed back; the message still present after reload; a reaction toggled into Turso and aggregated back; two sockets in one conversation exchanging a broadcast; handshake gates returning 401 for bad tokens, 101 for valid ones, 403 for wrong or missing origins. Test artifacts were deleted from Turso afterward. For the first time in the project's history, chat realtime was proven in production — and the method, not just the result, went into the repo's institutional memory.

15. Phase 12 — Evening hardening

Sessions: ses_feaac294 (evening portion), ses_fea56ad9 · Commits: worker 78bed4b, d5669b9; app 62cae06, a19ff48, 9a1155c, 3d99e17, bcdd083, b1c0b24

The user reported the next production bug from two devices: joining the same meeting showed no one else, ever. The investigation reproduced it live — two tabs, minutes apart, each seeing an empty room — while raw two-socket probes against the same meeting ID worked. Wire logs caught the cause: abnormal closes with code 1006 after silence. Cloudflare infrastructure drops idle WebSocket connections after roughly sixty to ninety seconds without a frame; nothing in the system ever pinged, so a device sitting alone in a meeting lost its socket invisibly, and the room emptied server-side while the screen still said connected.

Three fixes shipped as one batch:

  • 78bed4b — the worker pings every socket every 20 seconds, so no connection ever looks idle.
  • 62cae06 — every chat, meeting, and call socket gains a staleness watchdog: 45 seconds of silence force-closes and reconnects, with rejoin.
  • a19ff48 — meeting and call rooms renamed to meeting:v2: and call:v2:, because the existing instances still ran pre-heartbeat code — the same thirty-day pinning that bit chat.

The retest joined the user's live meeting, idled ninety seconds, counted sixteen pings and zero closes, then watched a second tab join and both show two participants. The day closed with documentation debt paid: AGENTS.md and DEPLOYMENT.md completed with real values, a HANDOFF.md added, and the worker repo given its own AGENTS.md. The production finalization report was committed, expanded with the ship sequence, and styled — the direct ancestor of the document you are reading.

16. Architecture as shipped

App — cloud-workspace (Vercel)
  • Next.js 16 App Router, React 19 with the React Compiler, Tailwind v4, Bun.
  • app/(workspace)/ route group per feature; app/api/ REST for chat, calls, meetings, files, tasks, workspace, recents, realtime tokens.
  • lib/auth.ts Better Auth 1.6 (GitHub, Google, credentials); RSC session reads.
  • lib/client-config.ts validates public URLs eagerly and throws on bad values.
  • Production guard in next.config.ts: required vars and HTTPS BETTER_AUTH_URL on real Vercel deploys; CSP allowlisting worker, PostHog, UploadThing.
Data and blobs
  • Turso (libsql) in production via @libsql/client/web; local SQLite in dev; env precedence fixed and fail-fast in prod.
  • Ten migrations; deploy-time db:deploy blocks releases on failure.
  • UploadThing for all blobs; 100 MB per-workspace quota at three layers; delete purges remote objects.
  • Chat tables in db/chat.ts, deliberately outside the Better Auth-generated schema.
Realtime — cloud-workspace-realtime (Cloudflare Worker)
  • One Durable Object class; all chat shares room chat2; conversations target conv:<id> and users user:<id> within it.
  • Meetings and calls use per-room instances: meeting:v2:<id>, call:v2:<id>.
  • Native WebSocket JSON protocol; contract mirrored in lib/chat-types.ts / lib/meeting-types.ts / lib/call-types.ts.
  • Gates: origin allowlist (ALLOWED_ORIGINS), short-lived JWTs signed with shared WS_AUTH_SECRET; 20-second pings keep sockets alive.
  • Chat writes persist to the same Turso database the app reads.
Client resilience
  • Chat falls back to REST sends plus 5-second polling whenever its socket is down.
  • All realtime sockets reconnect with backoff, rejoin rooms, and self-close after 45 seconds of silence.
  • Calls heartbeat every 15 seconds; a sweep inside listCalls ends calls idle past 90 seconds.

18. Failure patterns and lessons

18.1 Patterns that repeatedly caused trouble

  1. Localhost as source of truth. The guard relaxation (5862564), the worker's localhost-only ALLOWED_ORIGINS, and NEXT_PUBLIC_WS_URL=ws://localhost:3001 on Vercel were one failure wearing three outfits. The durable fix was architectural, not per-bug: one place holds production truth, and eager validation throws on divergence.
  2. Verification theater. Curl status codes, {"ok":true}, and passing builds stood in for product behavior. The realtime defect survived four days precisely because no check exercised it. Instrumented browsers closed the gap permanently.
  3. Fallbacks that mask failure. REST polling made dead realtime invisible. Resilience is valuable, but a fallback should surface degradation somewhere observable, not swallow it.
  4. Context poisoning through docs. AGENTS.md faithfully described the broken design into every future session's instructions. Documentation must be corrected in the same change that corrects reality, or it teaches the mistake forward.
  5. Concurrency without coordination. Same-day parallel sessions collided in files-view.tsx, the tasks layer, and the migration journal; the day-4 sweep mangled unrelated files and had to restore them from HEAD. Disjoint ownership helped; shared-file edits remained risky.
  6. Platform gotchas, learned by paying. HTTP/2 strips Upgrade headers (probe with --http1.1); Durable Objects pin creation-time code up to thirty days (version your room names); idle WebSockets die silently near 90 s (ping or perish); Vercel masks Sensitive vars and does not inline them into builds; empty-string env values defeat ?? defaults; drizzle-kit 0.31 dropped driver; Better Auth 1.6 sign-out takes no body; Next 16 params are Promises.
  7. Interrupted work counted as done. Aborted steps and forked readiness passes left no memory between attempts. The handoff-document habit (HANDOFF.md, worker AGENTS.md) is the antidote the project adopted.

18.2 What worked, and should be credited

  • Strict static gates on every change: tsc --noEmit, Biome, production builds. They caught hundreds of issues before runtime.
  • The orchestrator-plus-subagents pattern with disjoint directories and written contracts produced a shocking amount of correct software quickly.
  • Optimistic-UI correctness details — pending-send swaps, merge-not-replace fetch races, glare-free WebRTC negotiation — show review passes catching real distributed-systems bugs, not just typos.
  • Honest transcripts. The most valuable artifact of the whole project may be ses_febf8a7d's willingness to diagnose itself, name the band-aid in 5862564, and replace it with a principled guard.
