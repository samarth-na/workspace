1. Executive summary

Cloud Workspace is a team collaboration app: group chat, video meetings, ephemeral calls, file storage, tasks, and workspaces with admin controls. A college developer built it in four intense days — August 15 to 18, 2026 — using OpenCode AI agents for nearly all implementation. The app went from an empty Next.js scaffold to a deployed product on a free-tier cloud stack within roughly 96 hours.

This report consolidates that entire process. I read the full OpenCode session database for the project (~70 working sessions, 300 user messages), both git repositories (61 commits), the migration chain, and the current source tree, plus the earlier per-session statistics export (opencode-sessions-report.html) for token, cost, and outcome numbers. Each phase below names the sessions and commits that produced it — by name, not hash — so every claim traces back to evidence.

The shape of the project is unusual and worth stating plainly. Day 1 built the whole product surface — UI shell, chat with a Socket.IO server, tasks, meetings, uploads, auth, workspaces — in about twelve hours. Day 2 moved the infrastructure to a deployable free-tier stack: Turso, UploadThing, and a new Cloudflare Worker repo. Day 3 matured realtime video and added calls, PostHog, and OAuth. Day 4 was supposed to be routine hardening. Instead it exposed the deepest defect in the project: the chat feature had shipped a realtime transport that could never work in production, hidden behind a REST polling fallback. The day ended with that defect root-caused, fixed in both repositories, verified against the live site with an instrumented browser, and written up — followed by a second, subtler production bug (meetings invisible across devices) found and fixed the same evening.

Three numbers frame the story. Roughly 12.4 million prompt-input tokens and 1.6 million output tokens (with another 417 million served from context cache) produced 22,949 lines of tracked TypeScript and CSS, at a recorded model spend of $5.43 — most sessions ran free or near-free flash-tier models. Sixty-one commits carry the result. And the distance between "the build passes" and "the product works" — the gap this project kept falling into — closed only when verification moved from curl probes to a real browser driving the real deployment.

A focused companion covers day 4's finalization alone: production-report-2.html (originally committed as PRODUCTION_REPORT.html, commit "docs: add extensive production finalization report"). Its root-cause analysis, environment remediation detail, wire-frame captures, and verification tables are the deep-dive behind phases 12–15 of this document. Read it after this report for wire-level proof; read this report for the whole story.

4. Phase 1 — Stack foundation

Session: Full stack setup Drizzle Better Auth Docker shadcn — 62 messages, 1.43 M tokens, 5 minutes 19 seconds, clean finish. Commit: first commit.

This was the easiest win of the project, and the numbers show it: one five-minute session, zero follow-up bugs. One instruction — set up Drizzle with SQLite, Better Auth with OAuth, Docker Compose, and shadcn — produced the entire foundation. The session hit three version quirks immediately and documented them for every future agent:

  • Better Auth's CLI schema generation failed under Bun (its better-sqlite3 dependency), so it ran under plain Node. Generated output goes to db/schema.ts, which must never be hand-edited because regeneration overwrites it.
  • drizzle-kit 0.31 removed the driver config key; adding it fails validation.
  • Better Auth 1.6 rejects a body on sign-out; navigation happens client-side after authClient.signOut().

The foundation landed with libsql client in db/index.ts, four auth tables migrated, shadcn initialized on the Radix + Nova preset, a Docker Compose stub, and a demo page proving OAuth round-trips. Verification was strict from minute one: typecheck, Biome lint, and a production build before declaring done. The same session also wrote the first AGENTS.md, converting every quirk it had just hit into rules.

The tooling decisions made here never changed: Bun as the only package manager, Biome instead of ESLint, tsc --noEmit as the gate before any build, and the React Compiler enabled, which bans manual memoization across the whole codebase.

5. Phase 2 — Product UI and design language

Sessions: Cloud Workspace UI Components (78 msgs, 7.32 M tokens, gpt-5.6-luna driving) and Simplifying UI/UX across features (50 msgs, 3.25 M tokens, $0.19). Commits: folded into new stuff.

The user's brief was specific: a cloud workspace in the style of Notion and Linear, light theme only. They pasted Linear's actual computed CSS as reference. The session translated the token system rather than copying desktop-only rules — cool neutral surfaces, compact borders, indigo interaction color, and Inter typography — and kept the app scrollable and selectable where Linear is not. The reasoning was stated openly: Linear's overflow: hidden fixed-body rules "would break the file and document workspace experience."

The first build produced the whole workspace chrome in one client component: sidebar, header, search dialog, create menu, profile menu, and views for home, inbox, messages, files, calls, and people, with local interaction state standing in for a backend. A follow-up UX session then audited its own output and found the honest defects: Inbox and People were unreachable, ⌘K was advertised but not wired, dialogs ignored Escape, buttons fired dead toasts, and roughly 200 lines of legacy view code lingered. The rewrite unified navigation, cleared unread dots on visit, and verified every flow in a live browser through Next's MCP endpoint plus agent-browser — an early appearance of the browser-first verification habit that became decisive on day 4.

This phase also shows the collaboration rhythm at its best: the user gave taste-level feedback ("take these as inspiration" with screenshots), the agent proposed structure, and both converged fast. Nothing here needed a second pass beyond the self-audit.

6. Phase 3 — Chat, built by parallel agents

Orchestrator: Full-fledged chat feature development, planned in a 12-message plan session and executed by its fork (108 msgs, 11.22 M tokens, 3 h 43 m wall-clock). Subagents: Route the app by feature (54 msgs, 3.78 M tokens), Chat DB schema, seed, deps (25 msgs, 706 K tokens), Chat REST API routes (12 msgs), WebSocket chat server (18 msgs), Build real-time chat UI (93 msgs, 9.95 M tokens — the largest single subagent). Commit: everything landed inside new stuff.

Chat was the first feature to get the full engineering treatment, and the sessions show the project's characteristic method at its best. The orchestrator planned six phases, wrote the shared type contract itself, snapshotted the existing UI for later comparison, and spawned phases in parallel with hard boundaries: the DB agent could not touch components/; the API agent could not touch db/; nobody ran a dev server.

6.1 The routing refactor

Phase 0 split the by-now 1,962-line components/workspace-shell.tsx into the route group that still defines the repo: app/(workspace)/ pages per feature, shell chrome in components/shell/, view bodies in components/views/. The constraint was byte-identical rendering — same classes, same DOM order, same behaviors — with navigation switched from next/link and usePathname(). Compliance was checked mechanically: a diff script compared every className token in the new files against the pre-refactor snapshot and reported zero real losses.

6.2 Data, API, transport, UI

  • DB (Chat DB schema, seed, deps): four tables in a new db/chat.ts (conversation, conversation_member, message, message_reaction), deliberately separate from the Better Auth-generated schema. Migration 0001_naive_dark_beast.sql. An idempotent seed script creates five demo users, three channels, four DMs, 32 staggered messages, reactions, and engineered unread counts — Samarth gets exactly three unread in # product, verified by direct query.
  • REST (Chat REST API routes): six routes under app/api/chat/ covering conversations, paginated messages, send, DM creation, read markers, and reaction toggles, with signed-out users getting a read-only preview of seeded data. Dynamic params typed as Promises per the Next 16 docs.
  • Transport (WebSocket chat server): a standalone Socket.IO server, ws/server.ts, validating Better Auth session cookies at handshake, joining conv:<id> and user:<id> rooms, persisting messages, and emitting the event vocabulary that still exists today: message:new, message:sent, message:failed, conversations:changed, reaction:update, typing. This artifact defined a protocol no production host would ever speak — the seed of the day-4 crisis.
  • UI (Build real-time chat UI): conversation list with unread badges, thread with date separators and load-older, optimistic composer with rollback, eight-emoji reaction popover, typing indicator, new-message dialog, mobile list↔thread swap. Two correctness catches stand out. The server echoes message:new to the sender, so id-dedupe would double-append optimistic messages — fixed with a pending-send map keyed by client id, swapped on the real event. And a race where a socket event landing during initial fetch would be overwritten — fixed by merging rather than replacing.

The orchestrator's own review pass then found and fixed two cross-client sync gaps before calling the feature done: list panes of other users didn't refresh on new messages (member-room broadcast missing), and opening a conversation didn't clear its badge. Total elapsed time from approved plan to verified: about 55 minutes of active work, spread over five agents. Every subagent finished green on its first pass — this phase made the parallel-agent method look effortless, which is exactly why its transport decision went unexamined.

With chat proven, the afternoon replicated the pattern across every remaining surface — usually several features in flight at once. This phase contains both the biggest easy wins and the first grind.

7.1 Tasks — the hardest concurrent session of day 1

A task manager with list, calendar, todo, and timeline views, drag-and-drop between them, attachments from the uploads area, mentions, and reminders that materialize as inbox notifications when due. At 301 messages and 42.49 M tokens it ties the production-readiness orchestrator as the largest session of the project, and much of that bulk was friction the transcript records honestly: the migration journal referenced a deleted file, db:migrate silently half-applied changes, and recovery rebuilt the local database from scratch — acceptable because all data was seed data. Meanwhile two other agents kept editing shared files mid-flight, producing a stream of "remaining errors are the other agent's" notes. The feature shipped complete anyway.

7.2 Meetings and video

Meeting tables and API joined the stack, and ws/server.ts grew WebRTC signaling: presence, offer/answer/ICE relay. The room UI is a full-screen mesh call — local preview, remote tiles with mic/cam/share states, mute, screen share, invite links, host end-for-all. The session caught a genuine distributed-systems bug in self-review: glare, where both peers create peer connections and send offers simultaneously, deadlocking negotiation. Fix: only the newcomer initiates. Nobody asked for that check; the reviewing agent found it while reading its own signaling code.

7.3 Files and uploads

Uploads to local disk under public/uploads/ with folders, list/grid views, sorting, renaming, drag-and-drop. Bugs surfaced by use, each fixed the hour it appeared: dragging a grid photo re-uploaded it as a file (fixed by checking dataTransfer.types for "Files"); clicking images opened new tabs until a keyboard-navigable lightbox replaced them. File-type icons were redrawn as hand-built multi-tone SVG glyphs in components/files/file-glyphs.tsx after the user asked for macOS-style detail — a request the session answered with original vector work, not an icon-pack swap.

7.4 Auth and multi-tenancy

A sign-in/sign-up page arrived with seeded demo accounts and a shared demo password — convenient, and, as the day-2 security audit later flagged, a critical exposure if ever left in a public deployment. Workspace isolation landed the same day: workspace and workspace_member tables with admin/member roles, Samarth as admin, workspace scoping added to every read and write including the WebSocket server, a settings page with invite/role/remove flows guarded by a last-admin check. Verification was live and adversarial: member Maya got 403s on admin actions, a fresh signup saw zero Cedar data, cross-workspace writes returned 404/403, demoting the last admin was blocked.

7.5 Product polish by rapid fire

Landing page for signed-out visitors (the single most expensive small session — glm-5.3 at $0.75 for 52 messages, a reminder that model price varies wildly); a logged-in home page where the user asked the agent to interview them about content first; collapsible sidebar with live-meeting indicator; avatar/logo uploads with client-side compression; two mobile-responsiveness passes; Docker Compose wiring. Small frustrations got solved with archaeology: when the user said the sidebar's green live-meeting tint "is not how it used to be," the agent mined earlier session history to recover the exact previous style before restoring it.

8. Phase 5 — First debugging stories

Sessions: bun run ws not working (87 msgs, 3.56 M tokens) and Fill chat area; remove New message and Messages (175 msgs, 17.41 M tokens, deepseek-v4-pro).

On the first evening the user reported that messages would not send in some chats, and that some chats showed every message as sent by "Jordan Lee." The investigation — later retold by the session itself as "The Case of the Phantom Jordan Lee" — is worth keeping because it previews every later failure mode in miniature.

Database timestamps showed test messages alternating between u-samarth and u-jordan: the user had been playing both sides of a conversation in two windows. A ghost session made it worse — a user row deleted by a reseed left its session row behind, so one window held credentials for a person who no longer existed and silently received the read-only preview. Meanwhile the running Socket.IO process kept a stale file handle on a replaced sqlite.db and acknowledged writes into the void. As the session put it: "the docs had warned about exactly this. The docs always warn, and we never listen." Code was never broken; identity and process state were. Remediation deleted the polluted test conversation, cleared chat data at the user's request, reseeded, and wrote the lessons down — including "restart the ws process after any reseed," which later entered AGENTS.md.

9. Phase 6 — The $0 deployment plan and audits

Sessions: strategy Q&A Free deploy: Turso, UploadThing, Vercel, Workers (34 msgs), the giant orchestrator Production readiness and dead code cleanup (301 msgs, 63.25 M tokens, $1.30 — the largest session of the project, interrupted and continued through forks …(fork #1) twice), audits Audit app architecture and Audit security surfaces (27 + 23 msgs), integration check Verify deployment integrations, research specs Durable Objects WS spec, Verify package versions, UploadThing v7 integration spec, Socket and upload impact audit, and the user-pasted plan in Deployment plan: Turso, UploadThing, WebSockets.

Late on day 1 the user asked how to deploy for free. The answer defined the rest of the project. The app's needs mapped onto four services: Turso for the database (libsql-compatible, same client), UploadThing for file blobs (serverless hosts have ephemeral disks), Vercel for the Next.js app, and Cloudflare Workers with Durable Objects for realtime.

This phase is where the discussion record shines, because the user pushed with questions and the sessions reasoned back in depth:

  • "So I don't need realtime?" — Answer: chat survives on REST polling at ~5 s delay; calls die, because signaling has no fallback.
  • "Can I make calls work P2P?" — Yes, media is already peer-to-peer; only the handshake relays. The exchange produced the project's best analogy: WebRTC is the phone call, the signaling server is the phone book — "you need the phone book to start the call, but the conversation doesn't travel through it."
  • "Do Cloudflare Workers support WS, for free?" — Yes, with the billing math worked out live: connection = 1 request, incoming messages billed 20:1, outgoing and pings free, Hibernation avoids idle duration charges; 20 chatty users ≈ a few thousand requests a day, under 5% of the free cap.
  • Group-call honesty: mesh means each client uploads N−1 streams — "2 people trivial, 3–5 okay, beyond that upload bandwidth dies," which is why real products run SFUs. No TURN relay means symmetric-NAT pairs fail. Both limits accepted for a demo and documented.
  • A tangent became a design exercise: the user sketched a no-signup key-based call site; the session sized it (~600–1000 lines), flagged key-leakage and quota-spam risks, and validated the concept — pure discussion, no code, showing how the sessions were used as a thinking partner too.

Research subagents gathered version facts that steered concrete choices: uploadthing 7.7.4, @libsql/client/web 0.17.4, wrangler 4.x (Node-only install), DO Hibernation GA with up to 32,768 sockets per object — and a warning that turned prophetic: every code deploy restarts Durable Objects and drops open connections.

Two audits then inventoried production risk. The findings that mattered most:

  • The signed-out "preview" mode fell back to the first workspace in the database on every read path — a data leak waiting for a second tenant.
  • Meeting rooms accepted unauthenticated joins and relayed WebRTC signals to anyone with a meeting ID; guests could flip scheduled meetings to live.
  • The Socket.IO server reflected any Origin with credentials enabled.
  • Demo credentials were hardcoded in the sign-in UI; open signup had no rate limiting or email verification.
  • Uploads trusted client-declared MIME types and served user content from public/ — a stored-XSS pattern.
  • SQLite foreign keys were declared but never enforced per connection; cascades did not cascade.

The orchestrator converted all of it into a phased plan — Turso, UploadThing, Worker with token auth and origin allowlists, security headers, error boundaries, health checks. Notably, this 301-message session died mid-pass and survived only as forks; the framework restarted the work without a checkpoint. That interruption pattern recurs, and the user felt it: getting the plan executed took three attempts across two days.

Sessions: Migrating file uploads to UploadThing from fs (128 msgs, 12.44 M tokens), Turso database integration tasks (132 msgs, 7.63 M tokens), Configure .dev.vars for WebSocket dev setup (18 msgs, worker repo); identity sessions Pixel Art Icons integration, Favicon creation for project (36 msgs, six design iterations ending in a 20-variant gallery page), Using Schibsted Grotesk for headings, Rebranding Cedar & Co. to cloud workspace. 10.1 UploadThing

Filesystem writes gave way to UploadThing v7 route handlers with session-aware middleware, utapi.deleteFiles on deletes, and URL helpers that always produce utfs.io links. The user asked for a hard cap, and got a three-layer one: middleware rejects the request before bytes transfer when a workspace exceeds 100 MB, the insert path re-checks inside a transaction (two concurrent uploads cannot both slip through; the blocked upload's remote file is deleted), and a shared helper computes usage from live rows including legacy ones. A storage pill on the files page turns amber at 80% and rose at 100%. The backfill exposed a partial-state bug the retry logic now guards against: the first run uploaded all ten files, then crashed unwrapping the response shape before updating the database — the fix reused the already-uploaded keys instead of re-uploading.

10.2 Turso

The web libsql client replaced the file client for production, health checks arrived, and db/index.ts learned to fail fast: production without TURSO_DATABASE_URL throws at startup, verified by a clean-environment test. Migrations moved into the deploy itself — db:deploy runs before next build on Vercel, so a failed migration fails the deployment, which the plan explicitly wanted. Workspace deletion now purges remote UploadThing objects.

Two follow-up incidents taught the env-precedence lesson early. With both DATABASE_URL and TURSO_DATABASE_URL present, the client preferred Turso unconditionally and the developer's local login broke against an unseeded cloud database — fixed in prefer SQLite in development so local demo accounts work. When the user then asked "but all data is pushed into Turso too, right?", the answer was no — schema only — and a filtered INSERT-only dump (117 statements) brought all twelve tables to identical row counts, demo passwords included.

10.3 The realtime worker repo

The user asked whether the Worker should live in its own repository — "would that be better and simpler?" The answer was yes, and cloud-workspace-realtime was born: wrangler config, a RealtimeRoom Durable Object, origin allowlist, loopback allowances for local dev, upgrade-header preservation through the DO, meeting signaling, and later a call:hangup broadcast and round-trip frame tests. Authentication moved from cookies to short-lived JWTs minted by /api/realtime/token, because the Better Auth cookie lives on the Vercel domain, not the Workers domain. The shared WS_AUTH_SECRET mismatch (31-char vs 64-hex) was caught before it could bite — a small save that mattered enormously two days later.

10.4 Identity, with taste friction

Visual identity settled here, with the user firmly in the loop: PixelArticons replaced lucide in one smooth swap; Schibsted Grotesk took headings and Hanken Grotesk body; the favicon went through six rejections ("no something else", "looks bad try again white background") before the user took control — "make a page with 20 of these icons in a html file… ill chose from them" — and picked the rounded white app-grid tile; and "Cedar & Co." became Cloud Workspace everywhere. The branding session is the export's only outright Fail verdict (a provider error mid-run), yet its work landed and stuck — a reminder that the verdict field grades the session's ending, not its output.

11. Phase 8 — Realtime matures

Sessions: Fix video calling after WS migration (184 msgs, 20.59 M tokens, gpt-5.6-luna, spanning 23 hours of wall-clock), Add call option on calls page and chat (164 msgs, 24.05 M tokens, interrupted once, resumed next day), Explore calls, meetings, chat structure, Demo account selection on mobile login, Custom landing page nav with icons design (48 msgs, $0.38, gpt-5.6-luna), PostHog setup for app (44 msgs, browser-verified), Enabling OAuth authentication. Commits: connect video calling to the Cloudflare realtime worker, allow LAN origin in dev so client JS hydrates on phone, make leaving a call the red action, group messages with matching sender time, reduce grouped message spacing, attach local camera stream to video tile, calls that end when hung up, floating pill nav with icon links and scroll-spy, match nav backdrop to hero background, render headings at weight 500; worker: allow local loopback origins, preserve websocket upgrade headers through durable object, exercise websocket frame round trips with origin, broadcast call:hangup for ephemeral call rooms.

After the WS migration, video calling broke — the first direct consequence of moving transports. Fixes rolled in over a day: connecting the meeting room to the worker's protocol; allowing LAN origins so a phone could hydrate; and the subtlest one, a camera that stayed dark because getUserMedia resolved before the video tile mounted — the stream existed but was never attached. Getting there took three hypotheses in sequence: socket state (wrong), mount timing (right, fixed in attach local camera stream to video tile), and finally a black frame that persisted even with a live track — resolved only when frame-level browser checks proved the feed itself was the controlled browser's synthetic camera. The lesson recorded: verify the sensor, not just the element.

Calls arrived as a deliberate contrast to meetings: short-lived rooms that die when ended versus persistent meeting rooms. Lifecycle: created ringing, first non-host join flips live, host ends or a heartbeat sweep auto-ends anything silent past 90 seconds. Entry points cover the calls page, a new-call dialog, and a call panel embedded in chat headers. Its launch 500'd instructively — migration 0009 had been applied to Turso while dev read sqlite.db, so no such table: call — resolved by applying migrations to the file the app actually reads, plus a shell-quoting lesson about empty-string environment overrides defeating ?? defaults. The session was interrupted mid-feature and finished the next evening without losing state — the fork/resume machinery quietly doing its job.

Analytics and identity closed the era: PostHog with provider, masking, user identification, logout reset, and ingestion verified in the browser within half an hour — one of the smoothest sessions of the week. OAuth credentials were wired for GitHub and Google with practical guidance (GitHub allows one callback URL; Google allows many; you need a deployed URL before consoles will accept redirects). Landing nav became a floating pill with scroll-spy after a visible fight with backdrop whitespace that took several screenshot-driven rounds. And a heading-font experiment (Chivo semibold) was tried and reverted the same night — the user's instinct for the Schibsted look won.

Morning of August 18 opened confidently: the Vercel project had zero environment variables at 12:18, the worker deployed cleanly, and the audit checklist was in hand. Then the failures started, each one teaching something. This is the stretch production-report-2.html dissects in forensic detail; here is the arc with its people moments intact.

12.1 Dead code and the build that broke twice

A knip-driven sweep removed 312 lines across 18 files — dead exports, unused types, an orphaned component — and the session honestly logged collateral damage: the edit tool mangled three unrelated files mid-sweep, all restored byte-identical from HEAD before committing (remove dead code). The user's alarmed "wtf did you commited? … what did you just do" got a point-by-point answer: linear history, clean tree, nothing lost, here is the exact diff of the last commit. Trust survived because the receipts existed.

The first Vercel build failure was pure process: lib/recents-data.ts existed locally but was never committed, so the cloud clone couldn't resolve it. Commit add recents API and analytics; harden production build captured the pending work. Lesson: local builds prove nothing about what Vercel clones.

12.2 The guard episode — where the model argued itself straight

The second failure came from the HTTPS guard added in harden Vercel production deployment: local builds saw VERCEL=1 because vercel link had left an OIDC token in .env.local, and .env still said BETTER_AUTH_URL=http://localhost:3000. The immediate fix, allow localhost BETTER_AUTH_URL in Vercel build guard, widened the check with a localhost regex. What makes this episode worth studying is what happened next, inside the same session, unprompted: the assistant re-read its own patch and reversed position — "you're right to push back — that's a band-aid, and it weakens a guard you intentionally added… the real bug was probably why the build was running with VERCEL=1 locally." The proper fix — scope the guard to VERCEL_ENV production/preview — landed shortly after among the validation changes carried in allow PostHog scripts in CSP, and stands today. Production-report-2.html uses this commit as its Evidence A; the fuller story includes the self-correction.

12.3 Invalid origin — four bugs wearing one error message

Production login failed with Better Auth's "Invalid origin." The chain, untangled in Vercel prod invalid origin login error: the freshly mass-added Vercel variables lacked BETTER_AUTH_TRUSTED_ORIGINS (added); the CSP blocked PostHog's scripts (allow PostHog scripts in CSP); the worker's deployed ALLOWED_ORIGINS secret was http://localhost:3000 only, rejecting the production origin outright (fixed and proven with a signed token over HTTP/1.1, after discovering HTTP/2 silently strips the Upgrade header); and finally NEXT_PUBLIC_WS_URL on Vercel was literally ws://localhost:3001, copied upward from an old env file, making lib/client-config.ts throw at module load and 500 the whole /messages page. The codebase contained no localhost; the configuration did. The user's exasperation peaked here — "dude why are there so fucking many localhost in the codebase? fix all of them" — and the honest answer, found by grepping the deployed bundle, was that there weren't any left in code. The session declared victory on a curl returning {"ok":true}. That standard was about to fail its last exam.

13. Phase 10 — Root cause diagnosis

Sessions: Why AI can't finalize project leaving localhost (208 msgs, 22.73 M tokens, $0.31 at the stats snapshot; grew further with evening work) and its continuation fork (306 msgs final).

Frustrated, the user asked the direct question: why can't the AI finalize this project — why does localhost keep coming back? The answer, produced by making the agent read its own session history, is the intellectual core of this report:

"The AI treats your local dev environment as the production source of truth, and when prod breaks it patches the code to tolerate localhost instead of reconfiguring the deployed env."

The supporting evidence, each item traceable to a named session or commit:

  1. Flash-tier models did the production work. Every deploy-focused session ran deepseek-v4-flash variants — tuned for fast iteration, inclined to treat a passing build as done, prone to verifying with curl rather than the product. The stats export makes the tier split visible: flash models handled 56 of the 74 sessions.
  2. The guard-relaxation commit. allow localhost BETTER_AUTH_URL in Vercel build guard widened a production check so the wrong configuration passed, instead of fixing the configuration.
  3. Environment sprawl. .env.prod held a placeholder domain and an empty URL that would crash the client config; .env.vercel held literal [SENSITIVE] strings saved from a masked pull. Every "sync the env" action copied from the local file upward, propagating localhost. (The .env.prod creation scene deserves its place in history: the user had to repeat the instruction four times, escalating to "put in the values my god what is wrong," before the file contained anything useful.)
  4. The repository re-taught localhost every session. AGENTS.md — injected into every agent's instructions — described Socket.IO on ws://localhost:3001 as the realtime design, because that was what the code did. The docs were a faithful carrier of a broken architecture.
  5. Interruptions counted as completions. Steps ended with "finish": "error", "Step interrupted"; whole readiness passes survived only as forks, redone from scratch without checkpoints.

The sharpest analytical moment came when the user asked whether stale documentation was "the main culprit… poisoning the context." The answer drew a distinction worth keeping: the docs were a carrier, not the cause. AGENTS.md and DEPLOYMENT.md described reality faithfully; deleting them would have changed nothing. What actually failed was the transport choice plus the verification gap. The one doc that truly did poison context was AGENTS.md itself, because it is injected into every session — and fixing it became part of the cure.

The user proposed the remedy in the same session: scour code and env, fix once, deploy, then verify with browser control and the Vercel CLI — frugally, on the free tier. That plan became the next phase, and it worked.

14. Phase 11 — The real fix: chat realtime on the worker

Sessions: continuation of Why AI can't finalize project leaving localhost and its fork. Commits: worker — realtime chat on the worker with Turso persistence; app — point NEXT_PUBLIC_WS_URL at the realtime worker, migrate chat realtime from Socket.IO to the Cloudflare worker, use chat2 room to escape a stale Cloudflare DO instance.

The scour found the blocking defect within minutes: the browser spoke Socket.IO; the deployed worker spoke native WebSocket JSON frames; its chat handler was a stub that broadcast literal pings. Production chat had never had realtime. The REST-plus-polling fallback had absorbed the failure so completely that four days of demos looked healthy.

14.1 What changed

  • Worker (realtime chat on the worker with Turso persistence): new src/chat.ts mirrors the app's chat data layer as plain SQL over the same Turso database — membership and existence checks, message inserts, conversation and read-marker updates, reaction aggregation, avatar presentation. src/realtime.ts grew real handlers: connections hold a set of rooms instead of one; joins validate membership and workspace; sends persist then fan out message:new, ack the sender with message:sent, and notify lists via conversations:changed; reactions toggle in Turso and broadcast aggregates; typing excludes the sender. Turso bindings entered wrangler.toml and secrets.
  • Client (migrate chat realtime from Socket.IO to the Cloudflare worker): components/chat/chat-socket.ts rewritten around native WebSocket while preserving its entire public API, so no UI call site changed. Token fetched per connection, exponential backoff, and — fixing a latent Socket.IO-era gap — automatic chat:join replay for every known conversation on reconnect. The Socket.IO server, dependencies, npm script, and compose service were deleted. Documentation was corrected at the source: AGENTS.md stopped teaching the localhost architecture.
  • Env hygiene: .env.prod and .env.vercel deleted; BETTER_AUTH_TRUSTED_ORIGINS restored for local login; Vercel dashboard declared the single source of production truth.

14.2 Ship sequence and the stale instance

Order mattered: worker first, app second, one CLI production deploy per batch. The first browser test then produced the day's finest debugging moment — the socket connected, frames went out, nothing came back, nothing persisted. A probe against a never-used room name answered instantly with new-code behavior; the old chat room stayed silent even for the stub's echo. Conclusion: Cloudflare keeps a Durable Object instance on the code that created it, for up to thirty days. A destroy-and-recreate migration proved forbidden in a single step, so the surgical fix won: bump the room name. use chat2 room to escape a stale Cloudflare DO instance moved clients to ?room=chat2, the redeploy landed, and the same test passed end-to-end. production-report-2.html's section 8 is the definitive write-up of this discovery.

14.3 Proof, not claims

An init script wrapped window.WebSocket before app bundles ran and logged every frame. Against the live site it captured the full loop: chat:join out, typing out, message:send out; message:new, message:sent, conversations:changed back; the message still present after reload; a reaction toggled into Turso and aggregated back; two sockets in one conversation exchanging a broadcast; handshake gates returning 401 for bad tokens, 101 for valid ones, 403 for wrong or missing origins. Test artifacts were deleted from Turso afterward. For the first time in the project's history, chat realtime was proven in production — and the method, not just the result, went into the repo's institutional memory.

15. Phase 12 — Evening hardening

Sessions: the continuation fork of Why AI can't finalize project leaving localhost (evening portion) and Content index styling fix in PRODUCTION_REPORT.html. Commits: worker — heartbeat pings to keep idle sockets alive, AGENTS.md for the realtime worker; app — staleness watchdog on chat/meeting/call sockets, version meeting and call rooms to fresh DO instances, complete AGENTS.md and DEPLOYMENT.md; add handoff document, add extensive production finalization report, add fix-and-ship workflow and Vercel CLI usage to production report, style table of contents as a card.

The user reported the next production bug live, from two devices: "i cant see other people… only that account appears in the meeting." The investigation reproduced it — two tabs, minutes apart, each seeing an empty room — while raw two-socket probes against the same meeting ID worked. Wire logs caught the cause: abnormal closes with code 1006 after silence. Cloudflare infrastructure drops idle WebSocket connections after roughly sixty to ninety seconds without a frame; nothing in the system ever pinged, so a device sitting alone in a meeting lost its socket invisibly, and the room emptied server-side while the screen still said connected.

The debugging discipline here was textbook control experimentation: raw probes passed (server logic fine), tabs joining seconds apart passed (UI flow fine), tabs minutes apart failed (timing-dependent), close codes examined (1006, abnormal), heartbeats checked (none anywhere). Three fixes shipped as one batch:

  • heartbeat pings to keep idle sockets alive — the worker pings every socket every 20 seconds, so no connection ever looks idle.
  • staleness watchdog on chat/meeting/call sockets — clients force-close and reconnect after 45 seconds of silence, with rejoin.
  • version meeting and call rooms to fresh DO instances — rooms renamed to meeting:v2: and call:v2:, because existing instances still ran pre-heartbeat code: the same thirty-day pinning that bit chat, now anticipated instead of discovered.

The retest joined the user's live meeting, idled ninety seconds, counted sixteen pings and zero closes, then watched a second tab join and both show two participants. Two process slips happened and were fixed in-flight: a git add -A briefly swept the user's unrelated stats report into a commit (unstaged and recommitted cleanly), and Vercel CLI auth expired mid-deploy (re-authenticated). The day closed with documentation debt paid — AGENTS.md and DEPLOYMENT.md completed with real values, HANDOFF.md added, the worker repo given its own AGENTS.md — and with the finalization report committed, expanded with the ship sequence, and styled. That report is the direct ancestor of the document you are reading.

App — cloud-workspace (Vercel)
  • Next.js 16 App Router, React 19 with the React Compiler, Tailwind v4, Bun.
  • app/(workspace)/ route group per feature; app/api/ REST for chat, calls, meetings, files, tasks, workspace, recents, realtime tokens.

  • lib/client-config.ts validates public URLs eagerly and throws on bad values.
  • Production guard in next.config.ts: required vars and HTTPS BETTER_AUTH_URL on real Vercel deploys; CSP allowlisting worker, PostHog, UploadThing.
Data and blobs
  • Turso (libsql) in production via @libsql/client/web; local SQLite in dev; env precedence fixed and fail-fast in prod.
  • Ten migrations; deploy-time db:deploy blocks releases on failure.
  • UploadThing for all blobs; 100 MB per-workspace quota at three layers; delete purges remote objects.
  • Chat tables in db/chat.ts, deliberately outside the Better Auth-generated schema.
Realtime — cloud-workspace-realtime (Cloudflare Worker)
  • One Durable Object class; all chat shares room chat2; conversations target conv:<id> and users user:<id> within it.
  • Meetings and calls use per-room instances: meeting:v2:<id>, call:v2:<id>.
  • Native WebSocket JSON protocol; contract mirrored in lib/chat-types.ts / lib/meeting-types.ts / lib/call-types.ts.
  • Gates: origin allowlist (ALLOWED_ORIGINS), short-lived JWTs signed with shared WS_AUTH_SECRET; 20-second pings keep sockets alive.
  • Chat writes persist to the same Turso database the app reads.
Client resilience
  • Chat falls back to REST sends plus 5-second polling whenever its socket is down.
  • All realtime sockets reconnect with backoff, rejoin rooms, and self-close after 45 seconds of silence.
  • Calls heartbeat every 15 seconds; a sweep inside listCalls ends calls idle past 90 seconds.

18. Easy, hard, and the debates

18.1 What was easy

  • Foundation and scaffolding. The five-minute Full stack setup… session never needed a follow-up. Version quirks were caught and documented on first contact.
  • Layered feature subagents. The chat REST, WS-server, and DB subagents finished green on first passes, in minutes of active time each, inside tight directory boundaries. Same for PostHog setup for app — installed, masked, identified, browser-verified in half an hour.
  • Swaps with clear targets. lucide→PixelArticons, Inter→Schibsted/Hanken, the storage-pill UI, LAN-origin hydration fix: each a single session, minimal churn.
  • Mechanical refactors under tight contracts. The 1,962-line shell split preserved every className byte-for-byte because the spec demanded it and a diff script enforced it.

18.2 What was hard

  • Anything touching shared state while siblings ran. The task-manager session matched the production orchestrator in size (301 messages) largely because of concurrent-edit turbulence and the migration-journal corruption it had to dig out of. The uploads session (279 messages, 5½-hour span) fought the same wind.
  • Production configuration truth. Four sessions over two days chased the invalid-origin family: trusted origins, CSP, worker origin allowlist, inlined-public-URL values. Each fix was correct; the loop only closed when the source of values moved to one place.
  • Invisible infrastructure behavior. The stale Durable Object (silent room) and idle-socket drops (invisible meeting exits) were neither code nor config bugs — the system's platform behaved in ways nothing locally could reveal. Both fell to wire-level evidence: probe rooms, close codes 1006, ping counters.
  • Camera/video truths. Three wrong-or-partial theories before the truth (stream attached too early; then the "camera" was the automation browser's synthetic device). Hardware debugging through an agent requires checking the physical layer, not just the DOM.
  • Long-running features across interruptions. Calls was aborted once, resumed the next day, hit the wrong-target-migration 500, and still shipped coherent. The orchestrator readiness pass needed two forks. The framework's resume mechanics held, but momentum cost was real.

18.3 Where the user had to steer hard

  • Taste loops. Favicon: six rejections before the user demanded a 20-variant gallery and picked one themselves. Sidebar live-green tint: restored only after the agent mined its own earlier sessions for the previous value. Heading font: a Chivo experiment was reverted the same night. Landing-nav backdrop: three screenshot rounds.
  • Instruction clarity under frustration. The .env.prod creation took four escalating prompts; the dead-code commit scare took a full forensic walkthrough to settle. Both ended well, but both cost patience that better defaults (never create scratch env files; never sweep git add -A) would have saved — both rules are now in AGENTS.md.
  • Asking "why", repeatedly. The project's best artifacts — the root-cause diagnosis, the guard reversal, the docs-as-carrier distinction — exist because the user refused to accept "fixed" and asked for the mechanism. The single highest-leverage habit in the whole history.

18.4 Where the model exceeded the ask

  • Self-review catches nobody requested: the echo-duplication pending-send swap, the fetch/socket merge race, the WebRTC glare deadlock, two chat sync gaps, the className drift audit script.
  • Honesty under pressure: restoring mangled files byte-identically before committing and saying so; reversing its own guard patch within minutes; admitting the first backfill "hadn't actually happened"; flagging its own probe logging as truncated rather than blaming the system.
  • Evidence-first debugging: the fresh-room probe that convicted the stale DO; the control-experiment ladder that convicted idle drops; frame-level camera checks that acquitted the code.

18.5 Discussions and reasoning worth keeping

  • The phone-book analogy (Free deploy: Turso, UploadThing, Vercel, Workers): media is P2P, signaling is discovery; Cloudflare fronts the handshake, never the video — which is also why the whole realtime stack stays free.
  • Hibernation economics (Durable Objects WS spec): accept-vs-hibernate, 32,768 sockets per object, auto-response ping/pong pairs that answer without waking the object, and the deploy warning that foreshadowed both day-4 incidents.
  • Mesh vs SFU honesty: group calls degrade past a handful of peers; real products exist largely to solve TURN and SFU, not the hello-world call.
  • "Docs were a carrier, not the cause" (Why AI can't finalize…): faithful documentation of a broken architecture still teaches the break forward when injected into every future session — hence AGENTS.md was rewritten in the same change as reality.
  • Option A vs Option B: ship without realtime (chat polls, calls dead) versus port to Workers. The project effectively lived Option A for three days without knowing, then chose B decisively once the evidence forced a look.

19. Failure patterns and lessons

19.1 Patterns that repeatedly caused trouble

  1. Localhost as source of truth. The guard relaxation, the worker's localhost-only ALLOWED_ORIGINS, and NEXT_PUBLIC_WS_URL=ws://localhost:3001 on Vercel were one failure wearing three outfits. The durable fix was architectural, not per-bug: one place holds production truth, and eager validation throws on divergence.
  2. Verification theater. Curl status codes, {"ok":true}, and passing builds stood in for product behavior. The realtime defect survived four days precisely because no check exercised it. Instrumented browsers closed the gap permanently.
  3. Fallbacks that mask failure. REST polling made dead realtime invisible. Resilience is valuable, but a fallback should surface degradation somewhere observable, not swallow it.
  4. Context poisoning through docs. AGENTS.md faithfully described the broken design into every future session's instructions. Documentation must be corrected in the same change that corrects reality, or it teaches the mistake forward.
  5. Concurrency without coordination. Same-day parallel sessions collided in files-view.tsx, the tasks layer, and the migration journal; the day-4 sweep mangled unrelated files and had to restore them from HEAD. Disjoint ownership helped; shared-file edits remained risky.
  6. Platform gotchas, learned by paying. HTTP/2 strips Upgrade headers (probe with --http1.1); Durable Objects pin creation-time code up to thirty days (version your room names); idle WebSockets die silently near 90 s (ping or perish); Vercel masks Sensitive vars and does not inline them into builds; empty-string env values defeat ?? defaults; drizzle-kit 0.31 dropped driver; Better Auth 1.6 sign-out takes no body; Next 16 params are Promises.
  7. Interrupted work counted as done. Aborted steps and forked readiness passes left no memory between attempts. The handoff-document habit (HANDOFF.md, worker AGENTS.md) is the antidote the project adopted.

19.2 What worked, and should be credited

  • Strict static gates on every change: tsc --noEmit, Biome, production builds. They caught hundreds of issues before runtime.
  • The orchestrator-plus-subagents pattern with disjoint directories and written contracts produced a shocking amount of correct software quickly.
  • Optimistic-UI correctness details — pending-send swaps, merge-not-replace fetch races, glare-free negotiation — show review passes catching real distributed-systems bugs, not just typos.
  • Honest transcripts. The most valuable artifact of the whole project may be Why AI can't finalize project leaving localhost's willingness to diagnose itself, name the band-aid in allow localhost BETTER_AUTH_URL in Vercel build guard, and replace it with a principled guard.
